## 0. 先定边界：你要做的“像 Notion”到底是哪一部分

Notion-like 产品通常由 5 个层级组成（越往后越难）：

1) **单人文档编辑器**（块、层级、拖拽、/ 命令）

2) **数据库能力**（表格/看板/日历 + 属性类型 + 记录页）

3) **协作与权限**（分享、评论、多人编辑）

4) **搜索与规模化**（全文检索、权限裁剪、性能）

5) **AI 增强**（RAG/生成/批处理）

建议先做“能用的 1+2”，再做 3，最后做 4+5。

## 1. 产品拆解与里程碑（Roadmap）

### 1.1 里程碑定义（推荐）

- M0：技术预研（2-4 周）
- M1：MVP 单人编辑器 + 页面树 + 云端保存（4-8 周）
- M2：数据库（Table + 属性类型 + 记录页）与基础视图（6-12 周）
- M3：分享与权限、评论、审计（6-12 周）
- M4：实时协作（OT/CRDT）与稳定性（8-16 周）
- M5：搜索（倒排 + 权限裁剪）与大规模性能（6-12 周）
- M6：AI（RAG + 写作 + 数据库批处理）与评测体系（6-12 周）

### 1.2 “可发布闭环”验收口径

最小闭环：

- 用户注册登录
- 新建页面、编辑内容、拖拽重排
- 页面树导航
- 内容自动保存
- 共享链接只读访问

## 2. 技术选型（推荐组合，偏可落地）

> 你也可以替换为你熟悉的栈，但“数据模型与协作协议”不要轻易改。
> 

### 2.1 前端（Web）

- React + TypeScript
- 编辑器（二选一）：
    - **ProseMirror / Tiptap**：擅长富文本（inline），需要你自研块层
    - **Slate**：上手快，但大规模复杂编辑器的坑较多
- 组件库：自研 + 少量基础库（Radix UI / Floating UI）
- 状态管理：Zustand/Redux（任选）
- 表格/虚拟列表：react-virtual / tanstack virtual

### 2.2 后端

- API：REST（快）或 GraphQL（前端复杂取数更优）
- 语言：Node.js（NestJS/Fastify）或 Go/Java
- DB：PostgreSQL（强烈推荐）
- Cache：Redis
- 对象存储：S3 兼容（MinIO / AWS S3）
- 队列：BullMQ（Redis）/ RabbitMQ / Kafka（按规模）
- 实时：WebSocket（[Socket.io](http://Socket.io) 或原生 WS）
- 搜索：OpenSearch/Elasticsearch（后期）

### 2.3 协作（后期）

- CRDT：Yjs（推荐做 MVP 协作）
- 或 OT：自研难度高，不建议 0-1 首选

### 2.4 AI（后期）

- LLM：OpenAI/Anthropic/自建（按合规）
- RAG：倒排 + 向量混合检索（Hybrid）
- 向量库：OpenSearch kNN / Milvus

## 3. 核心数据模型（必须先定）：Page / Block / Database

### 3.1 页面树（Page Tree）

- `pages` 表：id, workspaceId, parentPageId, title, icon, cover, createdBy, createdAt, updatedAt, archived
- 页面层级：parentPageId 形成树；需要闭环检测与移动操作

### 3.2 块模型（Block Tree）

推荐用“块表 + 父子关系 + 有序列表”来表达：

- `blocks` 表：
    - id, pageId, type, props(JSONB), parentBlockId(NULL 表示顶层), position(可排序), createdAt, updatedAt
- 关键点：
    - **position** 用可插入排序键（例如 fractional indexing）避免频繁重排
    - props 存每种块的字段（文本、checked、url、style…）

块类型（MVP）建议：

- paragraph, heading1/2/3
- bulleted_list_item, numbered_list_item, todo
- toggle
- divider
- callout
- image/file（先做上传与引用）

### 3.3 行内富文本（Inline Rich Text）

两种实现路线：

1) 使用 ProseMirror：把文本与 marks（bold/link/mention）交给 PM 管

2) 自研 JSON 片段：`[{text:"hi", marks:["bold"]}, ...]`

MVP 建议：先做 1（成熟），不要自研富文本解析器。

### 3.4 数据库模型（后续）

核心实体：

- `databases`：id, pageId(容器页), name
- `properties`：id, databaseId, name, type, config(JSONB)
- `records`：id, databaseId, pageId(记录页)
- `property_values`：recordId, propertyId, value(JSONB)
- `views`：id, databaseId, type, config(JSONB)（filter/sort/group/layout）

## 4. 从 0 开始的实施步骤（按真实工程顺序）

## 4.1 Step 1：初始化项目与基础设施

**产出物**

- 单仓库（monorepo）或前后端分仓
- CI/CD：lint/test/build + staging 部署
- 基础监控：日志、错误上报（Sentry）

**关键决策**

- 单体后端先跑起来（更快）还是微服务（不建议 0-1）
- 数据库 schema 迁移工具（Prisma/MikroORM/Flyway）

**验收**

- 本地一键启动：`pnpm dev`（前后端 + DB）
- staging 环境可访问

---

## 4.2 Step 2：账号体系与工作区

**你需要实现**

- 注册/登录（email + password 或 OAuth）
- Workspace 创建（单用户也要有 workspace 概念）
- Session/JWT、CSRF（若 cookie）

**数据表**

- users, workspaces, workspace_members

**验收**

- 登录后进入“空工作区”，能创建第一页

---

## 4.3 Step 3：页面树（Sidebar）与路由

**你需要实现**

- 侧边栏展示页面树（递归）
- 新建/重命名/删除/移动页面
- URL 路由：`/page/:pageId`

**后端接口（示例）**

- POST /pages（创建）
- PATCH /pages/:id（改名、移动、归档）
- GET /pages/tree（取整棵树或按需加载）

**关键难点**

- 移动页面要防止循环引用
- 树的加载要支持“按需展开”避免一次取全

**验收**

- 侧边栏拖拽页面可改变层级与顺序（先做简单上下移动，后做跨层级）

---

## 4.4 Step 4：块编辑器 MVP（最关键）

### 4.4.1 先做“块壳”，再做“富文本”

推荐拆两层：

- **块层（block shell）**：每个块有手柄、菜单、拖拽、上下插入
- **文本层（inline editor）**：块内部的文本编辑

### 4.4.2 MVP 必做交互清单

- Enter：新段落
- Backspace：空块合并/删除块
- Tab/Shift+Tab：列表缩进
- / 命令：插入块（至少 heading/todo/divider/callout）
- 拖拽块重排
- 多选块（Shift + 点击 / 框选）可复制/删除
- Undo/Redo

### 4.4.3 数据保存策略（非常重要）

你需要选择：

- **增量保存（推荐）**：前端把操作转成 operations → 后端持久化
- **整页保存**：每次保存整棵块树（简单但性能与冲突差）

MVP 推荐“整页保存 + 节流”快速上线；但想做协作必须迁移到 operations。

**验收**

- 刷新页面后内容不丢
- 连续输入不会频繁请求（节流 300-800ms）

---

## 4.5 Step 5：文件上传与图片块

**你需要实现**

- 上传：前端直传 S3（pre-signed URL）
- 存储 file metadata：fileId, url, mime, size, owner
- 图片块引用 fileId

**验收**

- 图片可上传、预览、在页面中移动

---

## 4.6 Step 6：分享与权限（先做最简单）

### 4.6.1 MVP 权限模型

先只做 3 级：

- owner（创建者）
- editor（工作区成员）
- public_read（分享链接可读）

实现方式：

- `page_permissions`：pageId, subjectType(user/link), subjectId, role
- 分享链接：`share_tokens` 表（token → pageId → role=read）

**验收**

- 生成分享链接，未登录用户可只读访问

---

## 4.7 Step 7：数据库（Table 视图）从 0-1

按顺序实现：

1) 数据库容器（database page / inline database block）

2) 属性 schema（title/text/select/status/date/person/checkbox）

3) 记录（record）= 记录页（page）

4) Table 视图：

- 列显示/隐藏
- 单元格编辑（按类型）
- 行虚拟化

**验收**

- 能创建一个“任务表”，能新增任务、改状态、按状态筛选

---

## 4.8 Step 8：视图配置（过滤/排序/分组）

**你需要实现**

- view config JSON：filters[], sorts[], groupBy
- 前端 UI：filter builder
- 后端查询：把 view config 翻译成 SQL 查询（带分页）

**验收**

- 视图保存后再次打开仍生效

---

## 4.9 Step 9：Relation / Rollup / Formula（高难度，建议放后面）

### 4.9.1 Relation

- property type = relation(databaseId)
- value = related recordIds
- UI：搜索选择 + 新建关联项

### 4.9.2 Rollup

- 依赖 relation
- 定义：从关联记录取某字段并聚合（count/sum/...）

### 4.9.3 Formula

- 公式解析器（表达式）+ 执行器
- 建议：先做只读公式 + 小函数集（dateDiff, if, concat）

**验收**

- 项目表能汇总任务完成数

---

## 4.10 Step 10：评论、提及与通知

**你需要实现**

- block comment thread：commentId, pageId, blockId, authorId, content, resolved
- mention：在富文本中保存 mention entity（page/user/date）
- 通知：事件驱动（comment_created, mentioned）→ 写入 notifications

**验收**

- @人会在通知中心出现提醒

---

## 4.11 Step 11：实时协作（CRDT/Yjs 推荐）

**实施步骤**

1) 选定协作粒度：

- 只协作“文本块”还是整棵 block tree？

2) 建立协作通道：WebSocket

3) 前端：Yjs doc 与编辑器绑定

4) 服务端：

- room/session 管理
- updates 广播
- 定期 snapshot 持久化

5) presence：cursor/selection 单独通道

**验收**

- 两个浏览器同时编辑同一页，内容一致且不卡顿

---

## 4.12 Step 12：搜索（倒排 + 权限裁剪）

**实施步骤**

1) 抽取可索引文本：page title + blocks text + db property text

2) 建索引：OpenSearch/ES

3) 增量更新：

- 保存页面后发事件 → 索引更新队列

4) 权限裁剪：

- 索引中写入 workspaceId + allowedSubjects
- 查询时 filter

**验收**

- 搜索能秒级返回，且不会搜到无权限内容

---

## 4.13 Step 13：性能与稳定性（上线必做）

- 前端：
    - 虚拟化（数据库表）
    - 大页面分段加载
    - 图片懒加载
- 后端：
    - 读写分离（后期）
    - 缓存热点页面
    - 限流与防刷
- 数据一致性：
    - 幂等写入（尤其协作与批处理）
    - 失败重试（队列）

---

## 4.14 Step 14：AI（最后做，且必须有评测）

### 4.14.1 Web 端 AI 写作

- 输入：选区/当前块/当前页面
- 输出：块序列（标题/列表/段落）

### 4.14.2 RAG（对工作区问答）

- chunk：按块切分
- embedding：向量化存储
- 检索：关键词 + 向量混合
- 权限：只检索可访问 chunk
- 引用：答案要能链接回块/页面

### 4.14.3 评测

- 离线 eval：幻觉率、引用正确率
- 线上监控：延迟、成本、失败率、满意度

---

## 5. 关键难点与“踩坑清单”（强烈建议提前规避）

1) **富文本 + 块树 + 拖拽** 三者同时存在时，selection 容易错乱（尤其中文 IME）

2) **整页保存** 早期简单，但后期迁移到协作会很痛（最好尽早 operations 化）

3) **权限** 一旦上线就难改：务必先定义清楚继承与分享链接语义

4) **搜索权限裁剪** 必须从一开始就设计，否则会出现严重信息泄露风险

5) **数据库属性类型** 做得越多，单元格编辑器复杂度指数级增长（先做少数高频）

6) **公式/汇总/关系** 是“最吃时间”的部分，建议最后做

## 6. 推荐的“0-1 团队分工”

- 1 名前端：编辑器 + 数据库视图
- 1 名后端：数据模型 + API + 权限 + 文件
- 1 名全栈/平台：协作/搜索/队列/部署
- 1 名产品/设计：交互细节与可用性测试（否则会做成“能用但不好用”）
